# انتشار یک‌سرویسی ترب

این راهنما برای ریشهٔ کامل مخزن است، نه فقط `apps/api`. هیچ داده یا کلیدی داخل Git یا image قرار نمی‌گیرد. رابط ساخته‌شده و API از یک origin و یک سرویس Python ارائه می‌شوند؛ Vite proxy در انتشار استفاده نمی‌شود. طراحی رابط تغییر نکرده است.

## مسیر پیشنهادی: Docker و دیسک پایدار

از ریشهٔ مخزن `Dockerfile` را بسازید؛ مرحلهٔ Node با `npm ci` و `npm run build` فرانت را می‌سازد و مرحلهٔ Python وابستگی‌های قفل‌شده را از `requirements.txt` نصب می‌کند. فرمان پیش‌فرض `python -m tools.serve` است، روی `0.0.0.0` و `PORT` (پیش‌فرض ۸۰۰۰)، یک worker، بدون access log. image با کاربر غیر root، UID=10001 اجرا می‌شود.

پیش از اجرا، دیسک **واقعاً پایدار** را روی `/data` وصل کنید و دسترسی خواندن/نوشتن UID=10001 را بدهید. این دو فایل باید از مسیر جدا منتقل شوند:

- `/data/catalogue.sqlite3`: snapshot تاریخی موجود، بدون بازسازی/تغییر منبع.
- `/data/agent-usage.sqlite3`: دفتر مصرف موجود؛ نباید خالی، حذف یا برای انتشار reset شود.

برای گرفتن نسخهٔ سازگار SQLite، ترافیک مدل را هنگام انتقال نهایی متوقف کنید و روی دستگاه دارای فایل‌های اصلی اجرا کنید؛ مسیر خروجی باید **جدید** و خصوصی باشد:

```powershell
cd D:\starcoach\torob
.venv\Scripts\python.exe -m tools.export_deploy_data --output D:\torob-deploy-transfer-01
```

فرمان از SQLite backup استفاده می‌کند (شامل committed WAL)، فایل قبلی را overwrite نمی‌کند، integrity را بررسی و `manifest.json` شامل اندازه و SHA-256 می‌نویسد. هیچ آپلودی انجام نمی‌دهد. دو دیتابیس را با روش خصوصی میزبان مانند SSH/SCP به دیسک منتقل و SHA-256 را با manifest تطبیق دهید. فایل‌ها را داخل بستهٔ کد/پیام عمومی نگذارید. اگر دفتر مصرف فعلی ندارید، قبل از فعال‌سازی مدل روشن کنید سابقهٔ مصرف کجاست؛ ساخت دفتر تازه جای انتقال سابقه نیست.

برای نمونه روی میزبان Linux دارای Docker، پس از انتقال فایل‌ها به `/srv/torob-data` و تنظیم مالکیت UID=10001:

```sh
docker build -t torob-app .
docker run --rm -p 8000:8000 --mount type=bind,src=/srv/torob-data,dst=/data --env-file /secure/torob.env torob-app
```

`/secure/torob.env` فایل خصوصی سرور است؛ فایل محلی پروژه را خودکار آپلود نکنید. برای انتشار بعدی نیز **همان دیسک و دفتر مصرف** باید وصل شوند. پشتیبان‌گیری و سیاست نگهداری دیسک وظیفهٔ میزبان است؛ Dockerfile به‌تنهایی دیسک provision نمی‌کند.

## اگر میزبان Docker ندارد

ریشهٔ پروژه باید upload شود. Python 3.14 و Node 24 و ابزار npm در مرحلهٔ build لازم‌اند:

```sh
python -m pip install -r requirements.txt
npm --prefix apps/web ci
npm --prefix apps/web run build
python -m tools.serve
```

سه دستور اول build هستند؛ دستور آخر start است. پوشهٔ `apps/web/dist` ساخته‌شده باید در خروجی build به runtime منتقل شود. `TOROB_DATABASE` و `TOROB_USAGE_DATABASE` را به مسیرهای روی دیسک پایدار واقعی میزبان بدهید؛ `TOROB_WEB_DIST` فقط اگر dist جای دیگری است لازم است. نبود build، کاتالوگ معتبر یا دفتر موجود و قابل‌نوشتن باعث شکست روشن preflight و شروع‌نشدن سرور می‌شود؛ readiness هرگز فایل ledger غایب را از نو نمی‌سازد. برای dev همچنان فرمان قدیمی uvicorn/Vite معتبر است.

اگر مسیر انتشار لانچ‌لین امکان انتقال جداگانهٔ دادهٔ حدود ۳۹۱MB یا اتصال دیسک پایدار را ندهد، این محدودیت با تغییر نام فایل یا کد حل نمی‌شود؛ مسئول دیپلوی باید مسیر دارای این امکانات یا میزبان دیگری انتخاب کند. قابلیت‌های فعلی لانچ‌لین در این تغییر مستقلاً تأیید نشده‌اند.

## تنظیمات سرور

- `PORT`: پورت HTTP معتبر؛ معمولاً میزبان تنظیم می‌کند.
- `TOROB_DATABASE` و `TOROB_USAGE_DATABASE`: مسیر مطلق دو دیتابیس روی دیسک پایدار؛ پیش‌فرض Docker زیر `/data` است. خارج Docker پیش‌فرض‌های محلی قبلی حفظ‌اند.
- `TOROB_ASSISTANT_ENABLED`، `BOXAPI_API_KEY`، `TOROB_ASSISTANT_MODEL` و `TOROB_ASSISTANT_ATTEMPT_LIMIT`: تنظیمات فعلی دستیار. مقدار مدل/سقف در این تغییر عوض نشده؛ از مقادیر تأییدشدهٔ مالک استفاده کنید. تلاش‌های قبلی همچنان حساب می‌شوند.
- `TOROB_VOICE_ENABLED=1` و `AVALAI_API_KEY`: فقط در صورت تصمیم به فعال‌سازی صوت. endpoint پیش‌فرض صوت فعلی حفظ شده؛ `AVALAI_BASE_URL` در environment پیش از شروع process خوانده می‌شود.

در production همهٔ تنظیمات را از environment سرور بدهید. `.env.local` فقط allowlist قدیمی دستیار را می‌خواند؛ مسیر DB و صوت هرگز از آن auto-load نمی‌شوند. کلیدها را در build args، `VITE_*`، frontend یا Git نگذارید. بدون فعال‌سازی صریح، صوت/مدل فراخوانی نمی‌شوند.

## بررسی پس از انتشار

1. `/` باید HTML فرانت ساخته‌شده و فایل JS/CSS ارجاع‌شده در آن را با ۲۰۰ بدهد.
2. `/api/health/live` فقط زنده‌بودن process را نشان می‌دهد. `/api/health/ready` باید ۲۰۰ و checks کاتالوگ/دفتر/فرانت همگی `ready` باشد؛ نبود داده ۵۰۳ است، نه جست‌وجوی موفق خالی.
3. `/api/products?q=گوشی` و یک محصول/آفر واقعی را از همان origin بررسی کنید؛ سپس یک سفر دستی مرورگر بدون provider اجرا کنید.
4. یک restart و یک redeploy انجام دهید؛ snapshot و شمار تلاش‌های دفتر باید حفظ شوند. ابزار `python -m tools.report_usage --json` مسیر `TOROB_USAGE_DATABASE` را رعایت می‌کند؛ خروجی خصوصی است.
5. HTTPS برای میکروفون و مکان‌یابی مرورگر لازم است. reverse proxy میزبان باید HTTPS و forwarding را تنظیم کند. تست صوت/مدل واقعی نیاز به سقف مصرف تأییدشدهٔ جدا دارد.

ناوبری فعلی Workspace روی همان URL و history است؛ مسیر ساختگیِ ناشناخته به index بازنویسی نمی‌شود. API و `/docs` قبل از static قرار دارند؛ API ناشناخته یا asset گمشده ۴۰۴ می‌ماند. دیتابیس/کلید بیرون dist هستند و قابل دانلود از static نیستند.

این تغییر بسته‌بندی و مسیر اجرای محلی را آماده می‌کند؛ شاهد deploy واقعی، اتصال volume میزبان، شبکهٔ provider و سفر آنلاین فقط پس از اجرای مسئول دیپلوی قابل ادعاست.
