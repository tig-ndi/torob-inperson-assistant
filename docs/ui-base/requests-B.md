# درخواست‌های B از Base / هماهنگ‌کننده

**به‌روزرسانی D40:** کمبود صفحه‌بندی جایگزین‌ها در برش تأییدشده روی main ساخته شد: ادامه و retry همان offset، حفظ همهٔ آفرهای مستقل/گزارش اولیه، بررسی context و snapshot و برچسب نتیجهٔ قدیمی. request/DB/schema تغییری نکرد؛ شرایط دریافت در state فرانت فقط در حافظه‌اند. نتیجهٔ نهایی تست و محدودیت‌ها در EVALUATION/HANDOFF ثبت می‌شود. اشاره‌های پایین به باقی‌بودن این کمبود، سابقهٔ تحویل‌های قبلی‌اند.

## وضعیت پس از گام اتصال روی main — ۲۰۲۶-۱۰-۲۳

**به‌روزرسانی D39:** درخواست ۳ نیز در برش بعدیِ تأییدشده روی main پاسخ گرفت: Browser Back/Forward و Back داخل برنامه از یک history موقت استفاده می‌کنند؛ تست‌های موبایل/دسکتاپ حفظ اسکرول نتیجه، آفر مستقل دوم و پیش‌نویس را بررسی می‌کنند. منوی آزمایشی صفحه‌های Base حذف شد و مسیرهای عمومی کاربر جای آن را در تست گرفتند. شرح بازبودن درخواست ۳ در پاراگراف بعد، مربوط به وضعیت پایان برش قبلی است. صفحه‌بندی جایگزین‌ها و سرویس/خوانایی کاشی بیرونی همچنان جدا هستند.

با تأیید انسان و پس از ادغام PRهای A/B، درخواست‌های ۱، ۲، ۴، ۵ و ۶ در این گام پاسخ گرفتند: عنوان اختیاری پین در قرارداد؛ `MapViewProvider` با callbackهای رسمی sheet و focus؛ حذف پیام قدیمی Base؛ اتصال انتخاب همان product_id از A به B؛ و `data-layout` صریح پوسته به‌جای حدس از subtree. helper کلیک DOM حذف شد. حالت system نیز مطابق تنظیم واقعی مرورگر در A/B/نقشه هماهنگ است (D38).

درخواست ۳، Back/Forward مرورگر، هنوز اجرا نشده و در فهرست باقی‌ماندهٔ یکپارچه‌سازی ثبت است؛ دکمهٔ Back درون برنامه مستقل از آن کار می‌کند. درخواست ۷: فیلتر ظاهری CSS کاشی B حفظ شده، provider تیرهٔ تازه یا تضمین سرویس خارجی اضافه نشده است. درخواست ۹ دربارهٔ صفحه‌بندی جایگزین‌ها همچنان یک کمبود UI ثبت‌شده است، نه تغییر schema. شرح اولیهٔ زیر سابقهٔ تصمیم و درخواست B است.

این موارد در محدودهٔ مالکیت B نبودند یا بدون کارِ DOM/دور زدن قابل حل نبودند. B تا زمان تصمیم هماهنگ‌کننده با راه‌حل موقت و ثبت‌شده ادامه داد؛ هیچ فایل `base/`، registry، shell یا lockfile تغییر نکرد.

## ۱. نام فروشگاه در قرارداد `MapPin`

- **شاهد:** `apps/web/src/app/base/domain/mapPins.ts` فقط `label` قیمت و `offerIds`/`state` می‌دهد؛ نام فروشگاه در پین نیست. در نتیجه `MapLayer` برای tooltip/aria نام فروشگاه را از `state.loadedOffers` می‌خواند.
- **اثر:** وابستگی MapLayer به Workspace و نام‌گذاری تکراری منبع.
- **درخواست:** افزودن فیلد اختیاری `title` (نام نمایشی فروشگاه) یا معادل آن به `MapPin`، بدون تغییر معنی `offerIds`؛ یا تأیید صریح همین خواندن از Workspace.

## ۲. کنترل صریح sheet موبایل

- **شاهد:** `.ub-sheet-control` و state `sheet` داخل `WorkspaceShell` محلی‌اند. دکمهٔ «نمایش روی نقشه» B در موبایل باید ابتدا نقشه را آشکار کند؛ `apps/web/src/app/screens/b/revealMap.ts` دکمهٔ پوسته را از DOM کلیک می‌کند.
- **درخواست:** prop/context کوچک برای `setSheet('half'|'full')` یا callback `revealMap()` در mount point، تا B بدون دست‌زدن به DOM پوسته نقشه را نشان دهد. تا آن زمان راه‌حل موقت با کامنت ثبت شده است.

## ۳. Back مرورگر

- **شاهد:** `WorkspaceShell` فقط دکمهٔ Back درون‌برنامه را دارد و `popstate`/`history` را مدیریت نمی‌کند. B نمی‌تواند در فایل‌های خودش تاریخچهٔ مشترک را بدون عوارض مالکیت A تغییر دهد.
- **درخواست:** یکپارچه‌سازی `pushState`/`popstate` با `navigation` مشترک در پوسته؛ سپس B همان تست Back را برای مرورگر تکرار می‌کند.

## ۴. حذف یادداشت placeholder از صفحه‌های نهایی

- **شاهد:** `.ub-base-note` بالای outlet می‌گوید «صفحه‌های اختصاصی و نقشه هنوز در حال تکمیل‌اند»؛ روی صفحه‌های B خلاف واقع است.
- **راه‌حل موقت B:** قاعدهٔ محدود `.ub-base-note:has(+ .uv-visit)` در `screens/b/b.css` که فقط صفحه‌های B را هدف می‌گیرد.
- **درخواست:** حذف/جابه‌جایی این note در یکپارچه‌سازی A/B یا ارائهٔ prop برای پنهان‌کردن آن تا B به CSS `:has` وابسته نباشد.

## ۵. تطبیق نام محصول/دستهٔ A برای ورود به B

- **شاهد:** ورود فعلی B از طریق کارت preview مشترک A (`ContractPreview`) است؛ B فرض می‌کند `state.product` توسط A/ورودی واقعی تنظیم شده است.
- **درخواست:** تأیید mount point و قرارداد `product` میان A و B در یکپارچه‌سازی (بدون تغییر schema). B در نبود محصول، empty صریح نشان می‌دهد.

## ۶. حالت چیدمان اختصاصی B (Figma-like)

- **شاهد:** برای نزدیک‌شدن به Figma، B در دسکتاپ هدر Base را پنهان، search/filters را روی نقشه شناور، حاشیه/عرض پنل را بازتعریف و stepper کوچک Base را با stepper چهارمرحله‌ای B جایگزین می‌کند؛ همهٔ این‌ها با CSS محدود `:has(.uv-visit)` در `screens/b/b.css` انجام شده است.
- **اثر:** B ظاهر پوسته را فقط روی صفحه‌های خودش override می‌کند؛ این کار شکننده است و ممکن است با تغییر Base یا صفحه‌های A ناسازگار شود.
- **درخواست:** یک حالت صریح `layout="immersive"`/prop در shell یا mount point که هدر/stepper/search را برای B جابه‌جا کند؛ یا تأیید مالکیت این overrideهای CSS. هیچ فایل Base در این برش تغییر نکرده است.

## ۷. کاشی تیره و کنترل‌های نقشه

- **شاهد:** کاشی پیشنهادی OSM روشن است؛ Figma نقشهٔ تیره دارد. B با فیلتر CSS روی `leaflet-tile-pane` ظاهر تیره می‌سازد (`map.css`). این فیلتر رنگ برچسب‌ها/جاده‌ها را تغییر می‌دهد و یک provider رسمی تیره نیست.
- **درخواست:** تصمیم دربارهٔ provider تیرهٔ مجاز با attribution/شرایط استفاده یا تأیید همین فیلتر ظاهری. درخواست API key یا سرویس پولی مطرح نیست.
- **کنترل‌ها:** locate/theme/list در `MapLayer` هستند و state مشترک را dispatch می‌کنند؛ اگر shell دکمهٔ sheet رسمی بدهد، دکمهٔ list به آن وصل می‌شود.

## ۸. شکاف دادهٔ Figma (نه درخواست تغییر schema)

- Figma زمان پیاده/ماشین، ETA، «به‌زودی بسته می‌شود»، نقشهٔ داخلی پاساژ و تعداد مغازه‌ها را نشان می‌دهد. این‌ها با API فعلی پشتوانه ندارند و در B با metricهای صادق (فاصلهٔ هوایی/ساعت اعلامی/اعتبار اعلامی) و شاهد متنی جایگزین شده‌اند.
- اگر محصول به این قابلیت‌ها نیاز دارد، ابتدا قرارداد داده/سرویس معتبر و مجوز provider باید تعریف شود؛ B آن‌ها را جعل نکرده است.

## ۹. مواردی که درخواست تغییر Base نیستند

- `alternatives.has_more` با پیام صریح مدیریت می‌شود؛ افزودن صفحهٔ بعد در B با API موجود ممکن است و به Base وابسته نیست.
- خطای کاشی، GPS و HTTP با retry/حالت مستقل پوشش داده شده‌اند؛ هیچ endpoint یا schema تازه‌ای لازم نشد.
- outcomeهای شبیه‌سازی/گزارش کاربر همان قرارداد موجود P3-A هستند؛ درخواست فیلد «تأیید موجودی» یا «قیمت روز» ثبت نمی‌شود، چون API پشتوانه‌اش را ندارد.
