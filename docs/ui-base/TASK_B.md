# B — نقشه، فروشگاه و مراجعه

از همان SHA نهایی Base روی `codex/ui-b-map-visit` و checkout مستقل شروع کنید؛ A هم‌زمان فقط در محدودهٔ خودش کار می‌کند. قرارداد `base/` و `map/MapLayer.tsx` را پیش از تغییر بخوانید.

## مالکیت

فقط `apps/web/src/app/screens/b/`، `apps/web/src/app/map/`، `apps/web/unit/ui-b/`، `apps/web/tests/ui-b/` و `docs/ui-base/{log-B,requests-B}.md`.
exportهای `VisitScreen` و `MapLayer` و props آن‌ها حفظ شوند. CSS اختصاصی با prefix `uv-`/`um-` باشد. base، registry، lockfile، backend، تست‌های قدیمی و اسناد وضعیت عمومی تغییر نکنند. درخواست تغییر مشترک در requests-B ثبت شود.

## خروجی

۱. MapLayer واقعی با Leaflet و markercluster pin‌شده؛ CSS از پکیج محلی. از SVG/خیابان/محلهٔ ساختگی استفاده نشود. attribution نقشه زیر پنل مخفی نباشد؛ failure سرویس، فهرست را از کار نیندازد.
۲. pins و فهرست از `loadedOffers` و `pinsForWorkspace` مشترک باشند. پین گروه فروشگاه است و `offerIds` اعضا را حفظ می‌کند؛ کلیک آن، خودکار آفر دلخواه اول را تأیید نمی‌کند. همهٔ اعضای خوشه و آفرهای مستقل در دسترس باشند.
۳. همگامی کارت و پین با selectedOffer/focusedShopId؛ دوربین تنها با قصد روشن یا برای آشکارکردن انتخاب جابه‌جا شود. `cameraIntent`، padding، viewport و reduced-motion لحاظ شوند؛ مختصات برای بازکردن هم‌پوشانی جعل نشوند.
۴. Stores: `useOffers`، فیلتر/صفحه‌بندی سروری، شمار آفرها و فروشگاه‌های بارگذاری‌شده با برچسب درست، بدون ادعای پوشش همهٔ تهران. خطای سرویس با نتیجهٔ خالی یکی نباشد.
۵. پاساژ/طبقه/واحد فقط با `addressEvidence` و متن شاهد؛ ابهام را نشان دهید. ادغام دو ساختمان فقط بر اساس تشابه اسم یا مختصات کافی نیست. گروه پاساژ فقط اعضای مرتبطِ بارگذاری‌شده را نشان دهد؛ تعداد کل مغازه‌ها اختراع نشود.
۶. مقایسهٔ ۲–۳ آفر از همان محصول؛ CTA انتخاب واقعی را دنبال کند. compareOffers و visitPlan مستقل‌اند؛ مراجعه با یک فروشگاه هم ممکن است.
۷. Contact: `useSellerFollowup` و endpointهای موجود. prepare یعنی پیش‌نویس ارسال‌نشده، نه پیام ارسال‌شده. outcomeهای API فقط no_answer/closed/out_of_stock و source صریح simulated/user_report هستند. هیچ کانال تماس، شماره یا پاسخ فروشندهٔ ساختگی وجود ندارد. `SimBadge` و محدودیت‌ها تا پایان دیده شوند.
۸. جایگزین‌ها از `findAlternatives` بیایند، نه فقط فیلترکردن صفحهٔ فعلی. فروشگاه گزارش‌شده کامل حذف و همهٔ قیود حفظ شوند. no_alternatives با افزایش خودکار بودجه/شعاع جبران نشود.
۹. Trip: مقصد منتخب، جایگزین همان محصول، آدرس و شواهد متنی؛ خط مستقیم با برچسب «هوایی». لینک خارجی نقشه فقط پس از اقدام کاربر و با مختصات معتبر؛ ETA/مسیر خیابانی/زمان پیاده‌روی بدون سرویس معتبر نمایش داده نشود.

## مرزهای داده

قیمت تأییدشده، تنوع موجود فروشگاه، تماس واقعی و تأیید بیرونی در API فعلی وجود ندارند. چهار سناریوی نمایشی پروتوتایپ را با چهار واقعیت API یکی نکنید؛ برای نمایش فرضیِ تأیید/تغییر قیمت، ابتدا شکاف را گزارش کنید، نه اینکه schema یا قیمت منبع را خودسر تغییر دهید.
ساعت unknown بسته نیست؛ in_person_credit تطابق اعلامی است، نه تأیید اعتبار خریدار. انتخاب قدیمیِ خارج از فیلتر با `selectionNeedsReview` مشخص شود. با تغییر محصول، نتیجهٔ پیگیری/تأیید کالای قبلی منتقل نشود.

## پذیرش و بررسی

اولین فروشگاه قابل تصمیم در 320×568 و 390×844 دیده شود؛ پنل راه جایگزین بدون drag داشته باشد. map/list در عرض کافی کنار هم و در موبایل قابل تعویض باشند. keyboard/zoom/landscape و خطای map/GPS/HTTP بررسی شوند.
همهٔ اعضای خوشه، فروشگاهِ ساعت‌نامعلوم، چند آفر یک فروشگاه، null/قیمت بزرگ، انتخاب غیررتبهٔ اول، Back واقعی، تغییر فیلتر هنگام دریافت و شکست تا جایگزین آزموده شوند.
خودکار هزاران tile دریافت نکنید؛ تست‌های معمول با tile/network fixture انجام شوند و یک بررسی دستی محدود provider جدا ثبت شود.
build، test:ui-base، واحدهای B و مرورگر B اجرا و log-B با شواهد واقعی ثبت شود. raw QA محلی بماند. هیچ مدل پولی، تماس بیرونی، push یا تغییر remote انجام نشود؛ کامیت محلی منسجم با قالب پروژه مجاز است.
