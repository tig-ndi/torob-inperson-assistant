# قرارداد API کاتالوگ تاریخی — P1 و شرایط مراجعهٔ P2

به‌روزرسانی D25: پاسخ turn یک explanation اختیاری دارد و ورودی context_topics اختیاری است؛ جزئیات اتصال در بخش «توضیح مستند نتایج» پایین. UI فعلی این فیلد را هنوز نمایش نمی‌دهد؛ مالک اتصال پژمان است.

به‌روزرسانی بک‌اند P2 (D24، تکمیل D27): قرارداد درخواست/پاسخ بدون تغییر؛ مدل پیش‌فرض gpt-5.6-luna است و نام مدل در status/turn همچنان رشته می‌آید. بودجهٔ محاوره‌ای «بودجه‌م ۱۲٫۵ میلیون تومنه» دقیق خوانده می‌شود. برای لوازم جانبی بی‌هدف، سؤال نوع دستگاه پیش از سؤال زودرس بودجه است؛ مبلغ صریح نامعتبر همچنان نیازمند رفع ابهام است. نوع کالای روشن بدون بودجه جست‌وجو می‌شود و سؤال بودجه یا سؤال غیرضروری priority/product_kind فقط با عبارت کاملِ دارای پشتوانهٔ یک category_name واحد و سرِ سازگار به جست‌وجو تبدیل می‌شود؛ درخواست چندکالایی، ابهام دستگاه و بودجهٔ نامعتبر به سؤال می‌مانند. شواهد و آخرین آزمون واقعیِ باقی‌مانده در HANDOFF.

نسخهٔ محلی 0.1.0؛ فقط‌خواندنی، با مدل پاسخ strict. UI جست‌وجو/مقایسه/آفر/بودجه/محدوده و ساعات/شرایط ثبت‌شدهٔ خرید اعتباری ساخته شده‌اند؛ این API موجودی زنده، بازبودن تأییدشده، پرداخت یا تماس فروشنده ندارد.

## اجرا و تنظیمات

apps/web endpointهای کاتالوگ را مصرف می‌کند؛ فیلتر ساعات در همین مسیر آفر افزوده شده و مستقل از LLM/provider است. API قدیمی برای parser جدید UI کافی نیست؛ پس از تغییر کد سرور توسعهٔ Python را دوباره اجرا کنید.

نصب/run در README است. DB پیش‌فرض مستقل از cwd در ریشهٔ پروژه/.local/catalogue.sqlite3 است؛ متغیر اختیاری TOROB_DATABASE مسیر دیگر را تعیین می‌کند. .env خودکار بارگذاری نمی‌شود. اتصال mode=ro و query_only است؛ فایل ناموجود ساخته نمی‌شود. Uvicorn فقط روی 127.0.0.1 با --no-access-log اجرا شود. P1b از proxy Vite برای /api استفاده کند؛ CORS باز نداریم.

## endpointها

- `GET /api/products?q=گوشی&limit=20&offset=0&max_price_toman=10000000&category_name=گوشی+موبایل&category_cleared=false`: پاسخ items، has_more، limit، offset، category_name، provenance. query الزامی و حداکثر ۱۲۰ کاراکتر، بعد از نرمال‌سازی ۱–۱۲ واژهٔ حرفی/عددی؛ واژه‌ها literal با AND هستند. عملگر/prefix آزاد FTS نداریم. رتبهٔ FTS و product_id ترتیب را مشخص می‌کنند. فیلتر category_name پیش از LIMIT و OFFSET در SQL اعمال می‌شود و has_more بر مبنای دادهٔ فیلترشده است. اگر پارامتر category_cleared=true باشد، فیلتر دسته اعمال نمی‌شود و تشخیص خودکار غیرفعال می‌گردد. در غیر این صورت، اگر category_name ارسال نشود، دسته به‌طور قطعی بر مبنای ساختار هستهٔ اسمی (head-noun) از عبارت جست‌وجو تشخیص داده می‌شود.
- `GET /api/products/{product_id}`: پاسخ product و provenance؛ محصول شامل product_id، persian_title، brand_name، model، category_name، image_urls، specs و offer_summary است. مقایسهٔ ۲–۳ محصول در UI از همین endpoint استفاده کند. عنوان null/خالی و specs/image_urls خالی مجازند؛ fallback لازم است.
- `GET /api/products/{product_id}/offers?limit=20&offset=0&max_price_toman=10000000&user_lat=35.7&user_lon=51.4&max_distance_km=5`: items با offer_id، product_id، shop_id، price_toman، price_quality، last_price_changed_at، seller_title، description، warranty، inventory_status، direct_distance_meters و shop شامل name/address/location_label/lat/lon. contact یا لینک تماس خروجی ندارد. category-only در فروشنده‌های محصول وارد نمی‌شود.

مختصات کاربر (user_lat بین ۹۰- و ۹۰، user_lon بین ۱۸۰- و ۱۸۰) باید هر دو با هم ارائه شوند. تعیین max_distance_km نیازمند ارائهٔ هر دو مختصات است و مقادیر نامتناهی یا کمتر/مساوی صفر با 422 رد می‌شوند. فاصله با فرمول کروی Haversine (شعاع ۶۳۷۱ کیلومتر) پیش از گردکردن محاسبه و شرط شعاع قبل از LIMIT و OFFSET اعمال می‌شود. has_more بر مبنای نتایج فیلترشده است. فروشگاه‌های فاقد مختصات در صورت فعال بودن شعاع حذف می‌شوند و در نبود شعاع با direct_distance_meters=null باقی می‌مانند (نبود مختصات به معنی فاصلهٔ صفر نیست). direct_distance_meters عدد صحیح به متر است و صرفاً فاصلهٔ مستقیم هوایی است، نه مسافت یا زمان مسیر رانندگی/پیاده‌روی.

شناسهٔ محصول opaque و طول آن ۱–۲۰۰ کاراکتر بدون control character است. limit بین ۱ و ۵۰ و offset بین صفر و یک میلیون است. has_more برای صفحهٔ بعد؛ شمارش کل جست‌وجو انجام نمی‌شود. budget رشتهٔ ASCII با ۱–۱۹ رقم و حداکثر 9223372036854775807 است. اعشار/منفی/بزرگ‌تر 422؛ مقایسه با integer دقیق SQLite انجام می‌شود.

بودجهٔ جست‌وجو فقط محصول با حداقل یک آفر قیمت‌دار زیر سقف را نگه می‌دارد؛ قیمت نامعلوم واجد شرط نیست. **offer_summary همیشه کل آفرهای منبع محصول است**: offer_count، min_price_toman، max_price_toman و missing_price_count. UI عنوان «بازهٔ کل قیمت‌های ثبت‌شده» بدهد؛ برای آفرهای واجد سقف endpoint آفر را با همان budget فراخوانی کند.

آفرها قیمت عددی صعودی، null در انتها، سپس offer_id مرتب می‌شوند؛ این ترتیب ادعای بهترین فروشنده نیست. چند آفر یک shop/product با عنوان/ضمانت متفاوت محفوظ می‌مانند.

## ساعات مراجعه — گام نخست P2

در `GET /api/products/{product_id}/offers` پارامتر اختیاری `open_now_only=true` فقط آفرهای فروشگاه با وضعیت declared_open را نگه می‌دارد. پیش‌فرض false و همهٔ وضعیت‌ها قابل‌نمایش‌اند. فیلتر ساعت همراه بودجه/شعاع پیش از LIMIT/OFFSET اعمال می‌شود؛ ترتیب قیمت و حفظ همهٔ offer_idها تغییر نکرده است. زمان از سرور گرفته می‌شود و پارامتر عمومی تغییر زمان وجود ندارد. یک لحظهٔ ثابت برای همهٔ ردیف‌ها، predicate SQL و timestamp پاسخ هر درخواست استفاده می‌شود.

فیلد جدید صفحه `hours_evaluated_at` یک timestamp دارای offset به وقت Asia/Tehran است؛ حتی صفحهٔ خالی آن را دارد. زمان محاسبهٔ وضعیت است، نه زمان تأیید فروشنده یا به‌روزشدن برنامهٔ منبع. هر آفر `opening_hours` دارد:

پاسخ آفر Cache-Control: no-store دارد و fetch فرانت‌اند نیز no-store است؛ refresh نباید صفحهٔ زمان‌دار قبلی را از cache استفاده کند. زمان بررسی در UI تا ثانیه نمایش داده می‌شود.

- status: یکی از declared_open / declared_closed / unknown؛ همگی برداشت از برنامهٔ منبع‌اند.
- reason: within_declared_shift، outside_declared_shifts، declared_closed_day، missing_schedule، unsupported_schedule، invalid_schedule، no_valid_shifts یا previous_day_unknown.
- local_day: کلید mon…sun روز محاسبه‌شده در تهران.
- today_shifts و previous_day_overnight_shifts: بازه‌های معتبر با start_time/end_time در قالب HH:MM:SS و ends_next_day. لیست دوم شیفت‌هایی است که روز قبل شروع و روز جاری پایان می‌یابند؛ امروز ممکن است شیفت جدیدی نداشته باشد اما ادامهٔ شیفت دیروز هنوز فعال باشد.

شروع بازه شامل و پایان آن خارج است؛ بازهٔ شبانه روی دو تاریخ محلی محاسبه می‌شود. unknown برای برنامهٔ خالی/unsupported/ناسازگار/فاقد بازهٔ معتبر است. بازهٔ 00:00 تا 00:00 صفرمدت است و ۲۴ساعته تعبیر نمی‌شود؛ اگر کنار بازهٔ معتبر باشد حذف می‌شود، اما اگر تنها بازهٔ declared باشد وضعیت نامشخص است. closed همراه بازهٔ غیرصفر ناسازگار و unknown است. شیفت‌های روز با دادهٔ نامعتبر قابل اتکا نیستند. اگر شیفت معتبر فعلی یا ادامهٔ روز قبل بازبودن را نشان بدهد، declared_open است؛ در نبود بازهٔ فعال، برنامهٔ نامشخص روز قبل اجازهٔ نتیجه‌گیری قطعی بسته‌بودن نمی‌دهد (previous_day_unknown). این قواعد محافظه‌کارانهٔ محصول‌اند، نه تضمین یا تفسیر تأییدشدهٔ برگزارکننده.

unknown با closed فرق دارد؛ هر دو فقط با فعال‌کردن فیلتر ساعت از نتایج باز کنار می‌روند. UI علت و زمان بررسی را نشان می‌دهد و با «به‌روزرسانی وضعیت ساعت» درخواست جدید می‌فرستد؛ زمان به‌طور خودکار تازه نمی‌شود. تعطیلات، تغییر برنامه و بازبودن واقعی از این داده قابل اثبات نیستند. یک ساعت نامعتبر در منبع به unknown با reason صریح تبدیل می‌شود، نه نتیجهٔ خالی یا خطای کل سرویس. خطای DB/قرارداد سایر داده‌ها همچنان 503 است.

## دقت و منشأ

همهٔ قیمت‌های JSON رشتهٔ دهدهی‌اند؛ null همان null است. UI قیمت را برای محاسبه به Number تبدیل نکند و از BigInt/رشته استفاده کند. price_quality برابر missing، above_js_safe_integer (بیش از ۲^۵۳−۱) یا not_assessed است؛ این مدل تشخیص قیمت بازار نیست. تاریخ خام منبع حفظ شده؛ عنوان نمایشی «آخرین تغییر قیمت ثبت‌شده» با timezone تهران باشد، نه تأیید موجودی.

هر پاسخ موفق provenance دارد: snapshot_id (SHA-256 متن metadata.profile)، dataset، generated_at_utc، currency=toman و inventory_status=unconfirmed. خود آفر نیز unconfirmed است. generated_at زمان ساخت snapshot است، نه تأیید فروشنده. متن/URL منبع نامطمئن‌اند؛ HTML فروشنده اجرا نشود. ساعات و قیود اعتباری منبع ارزیابی می‌شوند؛ هیچ‌کدام تأیید زنده نیستند.

## شرایط خرید اعتباری حضوری — گام دوم P2

در مسیر offers، in_person_credit_only=true اختیاری است (پیش‌فرض false). فقط matches_declared_terms را پیش از LIMIT/OFFSET، همراه ساعت/بودجه/شعاع نگه می‌دارد. بدون این فیلتر همهٔ وضعیت‌ها باقی‌اند. ترتیب و offer_idهای چندگانه حفظ و has_more از نتیجهٔ فیلترشده است. پارامتر نامعتبر 422 است.

هر آفر in_person_credit با status، reason و options دارد. status یکی از matches_declared_terms / does_not_match / unknown است. reason کل یکی از matching_option، all_recorded_options_mismatch، incomplete_conditions، not_recorded یا invalid_data است. options تمام روش‌ها را با option_index صفرمبنا، provider_name، channel، min_price_toman/max_price_toman (رشتهٔ دهدهی یا null)، category_names (لیست رشته یا null برای اطلاعات خراب)، status و reason همان روش نگه می‌دارد. روش‌های هم‌نام ادغام نمی‌شوند.

reason روش: matched، channel_unknown، unsupported_channel، price_unknown، product_category_unknown، category_mismatch، below_minimum، above_maximum یا invalid_conditions. همهٔ کلیدها و قیود پیش از ارزیابی اعتبارسنجی می‌شوند؛ مبلغ منفی/اعشار/boolean/رشته در JSON منبع، بازهٔ وارونه، نام خالی و دستهٔ نامعتبر unknown می‌سازند. نمونهٔ خراب به نتیجهٔ معتبر خالی تبدیل نمی‌شود؛ وضعیت unknown با علت دارد.

تطابق فقط با channel=in_person، قیمت معلوم، قیود صحیح و دستهٔ مجاز همان محصول است. مرز مبلغ شامل است و مقایسه با integer دقیق انجام می‌شود. null در فیلد موجود یعنی قید مبلغ ثبت نشده، نه صفر یا اعتبار نامحدود واقعی؛ [] یعنی محدودیت دسته در منبع ثبت نشده، نه پذیرش قطعی هر کالا. key غایب unknown است. دستهٔ غیرخالی باید پس از نرمال‌سازی دقیقاً با category_name محصول برابر باشد؛ دستهٔ فعالیت فروشگاه/والد حدسی استفاده نمی‌شود. unknown channel حضوری فرض نمی‌شود.

وجود یک روش منطبق کافی است؛ بدون آن، وجود unknown وضعیت کل را unknown می‌کند؛ فقط عدم تطابق تمام روش‌ها does_not_match است. فهرست منبع خالی/غایب not_recorded است و نبود خدمت را اثبات نمی‌کند. UI فقط قیود ثبت‌شده را نمایش می‌دهد؛ تأیید اعتبار شخص، موجودی، پرداخت یا پذیرش فروشنده و هیچ اتصال واقعی provider در این قرارداد نیست.

## دستیار محدود — گام سوم P2

`GET /api/assistant/status`: ready، reason (ready/disabled/missing_key/invalid_config/attempt_limit)، model، remaining_calls و attempt_limit. این سهمیهٔ تعداد تلاش محلی است، نه موجودی دلاری پنل. کلید و مسیر فایل خروجی ندارد.

`POST /api/assistant/turn`: request_id با UUID کوچک‌نویس، messages با role=user/assistant متناوب (۱–۵ پیام، پایان user، هر محتوا ۱–۱۰۰۰ و مجموع حداکثر ۳۰۰۰ نویسه)، max_price_toman اختیاری رشتهٔ صحیح تا 9223372036854775807. context_query اختیاری/null با ۱–۱۲۰ نویسه، context_category اختیاری/null با ۱–۱۲۰ نویسه، category_cleared بولین (پیش‌فرض false). context_topics و context_battery_requirement اختیاری‌اند؛ قراردادشان در بخش‌های توضیح و ظرفیت آمده است. نقش system/tool و کلیدهای اضافی 422 هستند. تاریخچه/موضوع دادهٔ نامطمئن‌اند و server history ندارد؛ پیام‌ها/بودجه/موضوع به provider فرستاده می‌شوند، دادهٔ تماس و مختصات کاتالوگ خیر.

طرح مدل فقط action/query/budget_text/question دارد. query از enum حداکثر ۶ عبارت لفظی متن انسان است و host هم عضویت را می‌سنجد؛ ابزار آزاد و فیلد محصول/قیمت/شناسه مجاز نیست. در مسیر جایگزین قطعیِ سؤال بودجه یا سؤال غیرضروری priority/product_kind، عبارت کامل آخرین پیام پس از اعتبارسنجی ساختاری category_name (همهٔ واژه‌ها در یک دسته و واژهٔ اول سرِ همان دسته) می‌تواند مستقل از enum باشد؛ هیچ انتخاب اولین گزینه‌ای انجام نمی‌شود. budget_text نقل‌قول انسانی است؛ عبارت صریح یکتای سقف هم مستقیم parse می‌شود. مبلغ با Decimal/integer و تومان، نه حساب مدل، تعیین می‌شود؛ ریال/ابهام نیازمند سؤال است. سؤال‌های فارسی host از product_kind/budget/priority/specific_model ساخته می‌شوند.

query_choices از آخرین پیام دارای واژهٔ جست‌وجو ساخته می‌شود؛ واژه‌های کالای قدیمی با کالای جدید ترکیب نمی‌شوند. اگر پیام آخر فقط تغییر مبلغ/ادامهٔ کوتاه باشد، context_query بر تاریخچهٔ قدیمی مقدم است؛ بدون موضوع، پیام‌های قبلی از تازه به قدیم بررسی می‌شوند. این پردازش لفظی است و همهٔ ارجاع‌ها و کاربردهای زبان طبیعی را حل نمی‌کند. در product_kind clarification، query=null می‌شود تا عبارت مکالمه به موضوع تبدیل نشود. «بودجه را هشت میلیون کن» در زمینهٔ ورودی تومان به 8000000 تبدیل می‌شود؛ «ارزان‌ترش را می‌خواهم» بدون مبلغ جدید حتی با سقف قبلی و طرح search مدل، نیازمند سؤال بودجه است. همچنین برای درخواست‌های مشخصاً مبهمِ پشتیبانی‌شده (مانند «شارژر»، «باتری»، «کاور» یا «ساعت» بدون دستگاه هدف در متن یا زمینهٔ معتبر)، میزبان به‌طور قطعی سؤال تکمیلی product_kind (وضعیت needs_input) را تضمین می‌کند و از جست‌وجوی زودرس جلوگیری می‌نماید؛ در حالی که دسته‌های خارج از نگاشت کاتالوگ («کفش ورزشی») و فیلترهای حذف‌شده آزادانه و بدون توقف جست‌وجو می‌شوند.

اگر نوع کالا روشن باشد («کفش» یا «کفش کتانی»)، جست‌وجوی اولیه بدون بودجه مجاز است و توصیهٔ تناسب نیست. وقتی مدل با query=null سؤال بودجه می‌دهد، میزبان فقط کل عبارت محتوایی آخرین پیام را (حداکثر چهار واژه، بدون حذف واژهٔ تأییدنشده) می‌پذیرد اگر همهٔ واژه‌هایش پشتوانهٔ یک category_name واحد باشند و واژهٔ اولش سرِ همان دسته باشد، نه سرِ دستهٔ دیگر. پیش از حذف stopword، درخواست هم‌پایه/فهرستی با دو سرِ دستهٔ متمایز («شارژر و گوشی»، «گوشی، شارژر») و همچنین query جمع‌شدهٔ مدل برای چنین پیامی رد و به سؤال تبدیل می‌شود. بنابراین «گوشی کتانی»، «کفش گوشی»، «چیزی برای ورزش»، «کالای ورزشی» و کالای ساختگی به کوئری تبدیل نمی‌شوند؛ بودجهٔ متناقض/نامعتبر هم سؤال می‌گیرد. این استخراج ساختاری است و ترتیب/دستور/تناسب معنایی یا نام دستهٔ مرکب دوسطری را تأیید نمی‌کند. تبدیل غیربودجه فقط برای priority/product_kind و موضوع تأییدشده است؛ سؤال‌های clarify دیگر (battery_capacity/battery_scope/specific_model) override نمی‌شوند، ابهام دستگاه پس از تبدیل می‌تواند priority را به product_kind برگرداند، و یک call مدل است نه call دوم.

UI پس از نتیجه/نبود شواهد، موضوع و خلاصهٔ ثابت میزبان را حفظ می‌کند؛ برای turn بعد حداکثر دو زوج اخیر و پیام تازه ارسال می‌شوند. برای رعایت ۳۰۰۰ نویسه، زوج‌های قدیمی کامل حذف می‌شوند و موضوع جدا می‌ماند. جست‌وجوی دستی موفق نیز موضوع را تعیین می‌کند. «گفت‌وگوی تازه» موضوع/تاریخچه را پاک می‌کند ولی بودجهٔ آشکار بالا و cap تلاش‌ها را تغییر نمی‌دهد؛ refresh صفحه تاریخچه/موضوع را از دست می‌دهد. اولویت‌ها/کاربردهای قدیمی بیرون پنجرهٔ اخیر به حافظهٔ دائمی تبدیل نمی‌شوند.

دستهٔ زمینه fallback برای هر query تازه نیست: query همان موضوع یا برند/مدل لفظیِ موجود در همان دسته آن را حفظ می‌کند، ولی کالای تازهٔ خارج از نگاشت مثل کفش بعد از گوشی، دستهٔ گوشی را حمل نمی‌کند. تطبیق هویت از brand_name/model منبع و مستقل از بودجه است؛ قیمت پایین باعث تعویض با لوازم جانبی نمی‌شود. query کوتاه مدل هنگام رفع ابهام همراه متن کامل آخرین پیام سنجیده می‌شود؛ «شارژر گوشی» با query=شارژر نیازمند سؤال تکراری نوع دستگاه نیست. «گوشی پزشکی» زمینهٔ معتبر برای شارژر موبایل نیست. حذف فیلتر فقط بازیابی را کنترل می‌کند، نه وجود دستگاه در متن/زمینه؛ ابهام واقعی حتی با category_cleared=true سؤال می‌سازد.

در submit مستقیم، ویرایش بودجه بدون تغییر عبارت، category/category_cleared را حفظ می‌کند؛ عبارت تازه تشخیص خودکار تازه دارد. «گفت‌وگوی تازه» علاوه بر موضوع و تاریخچه، پرچم حذف دسته را برای درخواست تازه پاک می‌کند و بودجه/ledger را حفظ می‌کند.

پاسخ: request_id، status=needs_input/results/no_evidence، query، category_name، max_price_toman، question، products و model. needs_input سؤال و products=null دارد؛ results/no_evidence یک ProductPage واقعی با provenance، category_name و question=null دارند. query/بودجه/دستهٔ نهایی برای صفحه‌بندی بعدی همان endpoint قطعی products استفاده می‌شوند؛ هیچ فراخوان مدل برای صفحهٔ بعد لازم نیست. هر دو endpoint no-store هستند.

خطاها: 422 ورودی بد؛ 409 duplicate_request؛ 429 attempt_limit/busy؛ 503 disabled/missing_key/invalid_config/usage_unavailable/provider_auth/provider_rate_limit/provider_failed؛ 502 invalid_output/incomplete_output/provider_model_mismatch؛ 504 provider_timeout. خطای DB همان catalogue_unavailable است؛ هرگز no_evidence نیست. قطع client کار را لغو می‌کند؛ attempt رزروشده مصرف‌شده/احتمال هزینه باقی می‌ماند. client retry صریح درخواست جدید است؛ retry خودکار وجود ندارد.

مدل پیش‌فرض gpt-5.6-luna با low reasoning و حداکثر ۱۲۰۰ completion token، یک call و ۳۰ ثانیه برای مدل، پاسخ شبکه ۶۴KiB؛ query/data هم حدهای قبلی repository را دارند. ledger رزرو تراکنشی، UUID و یک تلاش فعال دارد؛ cap کلی با restart/reset گفتگو تغییر نمی‌کند. اگر مصرف/مدل در پاسخ گزارش نشود، نامعلوم باقی است و صفر/تأییدشده فرض نمی‌شود. مدل متفاوت پذیرفته نمی‌شود. هیچ نرخ رسمی یا سقف دلاری دقیق از cap تعداد قابل نتیجه‌گیری نیست.

## توضیح مستند نتایج — قرارداد افزودهٔ بک‌اند، D25

ورودی اختیاری `context_topics`: null یا فهرست حداکثر دو مقدار `camera`/`battery`؛ مقدار ناشناخته/نوع نامعتبر 422 است. null/حذف یعنی استخراج محدود از پیام‌های انسانی موجود؛ فهرست صریح بر تاریخچهٔ قدیمی مقدم و [] پاک‌کنندهٔ آن است. متن تازه می‌تواند موضوع را تغییر دهد؛ کالای غیرگوشی آن را پاک می‌کند. این فیلد انتخاب موضوع مرور شواهد است، نه قابلیت تأییدشده، فیلتر SQL یا مجوز حدس تناسب. پس از نتیجه، کلاینت می‌تواند `explanation.topics` را در turn بعد با این نام برگرداند؛ قبل از نتیجه حافظه همان تاریخچهٔ محدود است.

پاسخ `explanation`: برای needs_input برابر null؛ برای results/no_evidence، شیء با query/category_name/max_price_toman، ranking_basis=`lexical_match_then_product_id`، topics، summary/limitations، provenance و products هم‌ردیف محصولات صفحه (حداکثر۱۲). no_evidence فهرست محصول خالی دارد. مدل دوم، فیلتر یا رتبه‌بندی تناسب اجرا نمی‌شود.

هر عضو products شامل product_id، reasons، suitability=`not_verified`، budget_offer و topics است. با بودجه، budget_offer یک شاهد تاریخی واجد سقف شامل offer_id/product_id/shop_id/price_toman/last_price_changed_at/inventory_status=`unconfirmed` است؛ کمترین قیمت، سپس offer_id انتخاب می‌شود. مبلغ رشتهٔ ده‌دهی دقیق است؛ صفر صفر و null صفر نیست. بدون بودجه، budget_offer=null. انتخاب شاهد، سایر آفرهای یک فروشگاه/محصول را از endpoint آفر حذف نمی‌کند و موجودی زنده را ثابت نمی‌کند.

موضوع هر محصول دارای topic، status از recorded/missing/source_warning/conflicting/not_assessed، summary، evidence_count و evidence (حداکثر۴) است. هر نقل source_index صفرمبنا و section/key/value خام و state از recorded/negative/unknown دارد؛ جزئیات کامل در specs همان محصول موجود است. conflicting فقط برای نبود صریح و شاهد مثبت صریح هم‌عنوان استفاده می‌شود؛ هر متن غیرخالی تأیید قابلیت نیست. هشدارِ یک ویژگی جزئی، نبود همهٔ قابلیت‌ها را ثابت نمی‌کند. دامنهٔ فعلی فیلدهای شناخته‌شدهٔ دوربین/باتری گوشی موبایل است؛ سایر نیازها ارزیابی نشده‌اند. متن‌ها دادهٔ نامطمئن‌اند و باید در UI به‌صورت متن امن نمایش داده شوند.

کلاینت فعلی بدون شکست فیلد پاسخ اضافه را نادیده می‌گیرد. پژمان باید parse/type و نمایش توضیح و حمل context_topics را در branch UI وصل کند؛ هیچ فایل وب در این گام تغییر نکرد. خطای منبع لازم برای توضیح 503 با catalogue_unavailable است، نه نتیجهٔ موفق خالی.

## حداقل ظرفیت باتری گوشی — D26، قرارداد تحویل UI

`GET /api/products` پارامتر اختیاری `min_battery_capacity_mah` دارد: عدد صحیح ۰ تا ۱۰۰۰۰۰۰، واحد mAh. سقف صرفاً مرز ورودی است، نه تعریف ظرفیت خوب. مثال: `q=گوشی&min_battery_capacity_mah=5000&max_price_toman=8000000`. فیلتر >= در SQL پیش از صفحه‌بندی و مستقل از بودجه اجرا، و در ProductPage با همین نام بازگردانده می‌شود. هر صفحه باید همان مقدار را دوباره بفرستد؛ offset فقط بین نتایج واجد شرط است. با حذف پارامتر شرط حذف می‌شود.

دامنهٔ معیار فقط `گوشی موبایل` منبع است. category_cleared=true یا category_name=null، شرط مستقل ظرفیت را حذف نمی‌کند؛ این شرط ذاتاً نتایج را به گوشی با ظرفیت معلوم محدود می‌کند. اعمال روی نوع مشخص دیگر 422 است. مقدار نامعلوم، متناقض، بدون واحد، بازه یا غیرقابل‌تفسیر در فیلتر پذیرفته نمی‌شود. «در نتایج نیست» اثبات ظرفیت پایین یا نبود محصول/موجودی نیست.

Product (و نسخهٔ آن در detail) دارای `battery_capacity` است: status از known/unknown/conflicting/not_applicable؛ capacity_mah فقط برای known عدد و در سایر حالات null؛ reason، evidence_count و evidence حداکثر۴. شاهد شامل source_index، section/key/value خام و parsed_mah عدد یا null است. refs کامل در specs باقی است. تعارض، یا ترکیب دادهٔ دقیق با ادعای غیرقابل‌تفسیر، known نیست. واحد صریح در value یا کلید پرانتزی منبع، mAh/Ah و معادل فارسی پشتیبانی می‌شود؛ تبدیل Ah دقیق است. null/نامعلوم صفر نیست. حداکثر چهار شاهد مهم، از جمله دو طرف تعارض، برای نمایش اولیه نگه داشته می‌شود.

ورودی اختیاری turn: `context_battery_requirement` با شکل `{"status":"minimum","minimum_mah":5000}`. status می‌تواند unspecified/awaiting_minimum/no_minimum/minimum باشد؛ minimum دقیقاً یک عدد صحیح در بازهٔ بالا می‌خواهد، سایر حالت‌ها minimum_mah=null دارند. خروجی هر turn همین state را در `battery_requirement` می‌دهد. حذف ورودی/null یعنی استنتاج محدود از تاریخچه؛ `{status:"unspecified",minimum_mah:null}` صریح، زمینهٔ قدیمی را کنار می‌گذارد ولی متن جدید همچنان بررسی می‌شود.

برای گوشی با «باتری قوی/خوب» سؤال battery_capacity و state awaiting_minimum می‌آید؛ حداقل فرضی وجود ندارد. «حداقل ۵۰۰۰ میلی‌آمپرساعت» یا «حداقل ۵ آمپرساعت» معتبر است. عدد بدون واحد فقط در پاسخ به سؤال مشخص ظرفیت، mAh است. عدد ظرفیت به بودجه تبدیل نمی‌شود. مقدار دارای واحد ولی بدون تعیین حداقل، بازه/چند مقدار/واحد نامعتبر سؤال روشن‌سازی می‌گیرد. «بدون حداقل» در پاسخ به سؤال، یا «فیلتر ظرفیت باتری را حذف کن» state no_minimum و جست‌وجوی بدون این شرط می‌دهد. «باتری قابل تعویض» خودبه‌خود شرط ظرفیت نیست.

تغییر بودجه/برند در همان گوشی state را حفظ؛ تغییر نوع کالا و گفت‌وگوی تازه آن را پاک می‌کند. شرط صریح روی نوع غیرگوشی سؤال battery_scope می‌گیرد؛ با پاسخ «بدون این شرط» و context_query معتبر، آن نوع کالا بدون شرط جست‌وجو می‌شود. برای کالای تازهٔ روشن، جست‌وجوی اولیه بدون بودجه مجاز است؛ سؤال بودجه‌ای که مدل با query=null بدهد فقط با عبارت کامل و معتبرشدهٔ نوع کالا (بند دستیار بالا) به جست‌وجو تبدیل می‌شود. عبارت عمومی/مبهم و کالای تأییدنشده سؤال می‌ماند و بودجهٔ متناقض/نامعتبر سؤال می‌گیرد. این رفتار در آزمون واقعی تازه و UI هنوز پذیرفته نشده است.

explanation شامل min_battery_capacity_mah و برای هر محصول battery_capacity و دلیل تطابق حداقل است. داده، تاریخی و غیرقابل‌اعتماد به‌عنوان دستور است؛ نمایش فقط به‌صورت متن امن. مقدار ظرفیت، دوام واقعی یا توصیهٔ کیفی را اثبات نمی‌کند و suitability=not_verified باقی می‌ماند.

**کار لازم در branch پژمان:** type/parser و نمایش حالت سؤال/شرط فعال، کنترل حذف/ویرایش، ارسال battery_requirement پاسخ به‌عنوان context_battery_requirement در turn بعد، و ارسال min_battery_capacity_mah در تمام درخواست‌های صفحه‌بندی/ویرایش بودجه. با گفت‌وگوی تازه state را کنار بگذارید؛ پاسخ دیررس state جدید را بازنویسی نکند. کلاینت فعلی این اتصال را ندارد؛ fallback تاریخچه جای حفظ صریح state در مسیرهای طولانی یا صفحه‌بندی نیست. UI این گام تغییر نکرده است.

## اصلاح تفسیر شرط و مبلغ — D28 / BE-001 تا BE-003

قرارداد JSON تغییر نکرده است. «فیلتر ظرفیت باتری را حذف نکن، فقط بودجه را هشت میلیون کن» شرط فعال را نگه می‌دارد؛ «دوربین مهم نیست» باتری را حذف نمی‌کند؛ «باتری حداقل ۵۰۰۰ mAh و بودجه حداکثر ده میلیون تومان» هر دو شرط را مستقل اعمال می‌کند. حذف مثبتِ صریح همچنان شرط را پاک می‌کند. فرمان متناقض حذف/حداقل به سؤال ظرفیت و products=null می‌رسد؛ جست‌وجوی بی‌صدا بدون شرط انجام نمی‌شود. مرزهای نشانه‌گذاری و ربط محدودند؛ تحلیل جامع نفی و ارجاع ضمیر ادعا نمی‌شود.

بودجهٔ صریح منفی با علامت یا واژهٔ «منفی»، حتی با budget_text=null مدل، needs_input با سؤال بودجه می‌دهد و retrieval انجام نمی‌شود. مقدار بودجهٔ فعال تا روشن‌سازی حفظ می‌شود؛ نبود واقعی بودجه با بودجهٔ نامعتبر فرق دارد و همچنان طبق سیاست قبلی قابل جست‌وجو است. عدد منفی با واحد باتری، خودبه‌خود مبلغ پول نیست.

parse_toman بدون float یا گردکردن، فقط نتیجهٔ صحیح نامنفی تا 2^63−1 را می‌پذیرد. ۰٫۵ میلیون تومان برابر ۵۰۰۰۰۰ است؛ 0.99999999999999999999999999999 تومان کسر است و سؤال بودجه می‌گیرد، نه تبدیل به ۱. صفر و مبالغ بزرگ رشته‌ای دقیق باقی‌اند. این قواعد backend هستند و نیاز به تغییر نام فیلد یا schema فرانت ندارند.

## خطا و بازیابی

- 200 با items خالی: مدرکی مطابق query/filter در این صفحه نیست.
- 404: محصول در snapshot نیست؛ محصول موجود بدون آفر 200 و لیست خالی است.
- 422: ورودی نامعتبر؛ UI فیلترها را برای اصلاح حفظ کند.
- 503 با code=catalogue_unavailable: DB ناموجود/خراب/ناسازگار، سقف اجرای SQLite یا nested data نامعتبر. نتیجهٔ خالی نیست؛ مسیر و snapshot بررسی و سپس retry شود. متن حساس منبع در خطا افشا نمی‌شود.

detail خطای 422 استاندارد FastAPI ممکن است رشته یا لیست باشد؛ UI فرض رشته نکند. پاسخ دیررس با AbortController کنترل می‌شود. مسیر محلی جست‌وجو/مقایسه/آفر/بودجه/محدوده و ساعات در Chromium بررسی شده؛ شواهد جاری در HANDOFF است و deployed journey نیست.
